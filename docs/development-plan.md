## 1. 本書の目的

どの順番で作るか（段階）と、1 つの Pull Request で何を作るかを決め、いまどこまでできたかが分かるようにする。何を作るかは[要件定義書](requirements/requirements.md)と[機能定義書](functions/function-definition.md)、どう作るかは[基本設計書](design/basic-design.md)と[技術スタック定義書](tech-stack.md)で決めている。

## 2. 進め方の方針

**機能ごとに、API（バックエンド）とそれを使う画面（フロントエンド）を 1 つの Pull Request で作る。**

| 段階 | 作るもの | 理由 |
| --- | --- | --- |
| 段階 1 | 土台と、機能ごとの API と画面（FN-01〜FN-14、G-1〜G-18） | 1 つの機能を API のテストで固めたら、すぐに本物の API につないだ画面で確かめられる。画面で見つけた問題を、同じ Pull Request の中で API に直せる |
| 段階 2 | 通しのテストと公開、受け入れ | 登録 → ワークスペース → 招待 → チャンネル → メッセージ（リアルタイム・スレッド・添付・リアクション・メンション）→ DM → 検索 → 通知 の流れを、2 人分の画面から自動のテストで確かめ（要件定義書 13 章の検収のためのテスト）、AWS に公開して検収する（P-5・13 章） |

BookLog と同じく、次のものは最初から入れる。

| もの | 入れ方 |
| --- | --- |
| API の仕様書（OpenAPI。基本設計書 2.1） | 1-1 で仕組みを入れ、各機能の行で API と一緒に仕様書と画面の型を更新する |
| リアルタイムの通知の型（基本設計書 2.1） | 1-5 で仕組み（サーバーの record と画面の型、読めることを確かめるテスト）を入れ、各機能の行で通知を足すたびに更新する |
| 層ごとの単体テスト | 各機能の行で、API を通したテスト（MockMvc・Testcontainers）に加えて、Controller・Service・Repository（画面は関数・hook・部品）を 1 つずつ確かめるテストも書く |
| 見られるかの確かめ（データ設計書 8.1、BR-2） | 1-3 で 1 つの部品にまとめ、以降の行はすべてこれを使う。各行で「見られない人からは取れない」テスト（API・購読・検索）を書く（要件定義書 R-5） |
| 構造化ログ（基本設計書 2.3） | 1-1 で入れる。WebSocket のログは 1-5 で足す |

- 機能どうしの関係で、ある機能の画面の一部が後の機能の API を使うときは、その API を作る行で画面も仕上げる（例：G-16 の「メッセージを送る」は 1-9）。それまでの画面は、その機能で確かめられる範囲だけを出す
- 動きは、API のテスト・画面のテストと、本物の API につないだ画面（Chrome DevTools。375px の幅も）で確かめる。リアルタイムの通知は、2 つのブラウザ（別の人）を同時に開いて確かめる

## 3. 作る順番

1 行を 1 つの Issue・1 つの Pull Request にする。行に取りかかるときに Issue を立て、その Pull Request の中で「Issue」の欄に番号を書いて「状態」を ▶ にし、終わったら ✅ にする（状態の欄だけは、その行の Pull Request で直し忘れたときに、次の行の Pull Request で直してもよい）。

状態：✅ 終わった、▶ 作業中、空欄 まだ

## 5. 進め方の決まり

- 開発のルール（Issue → ブランチ → Pull Request → 自動レビュー → squash マージ）は [CONTRIBUTING.md](../CONTRIBUTING.md) のとおり
- 作っている途中で仕様を変えるときは、同じ Pull Request で文書も直す（[CLAUDE.md](../CLAUDE.md)）
- 順番を変えるときや、行を分ける・まとめるときは、本書の版数を上げて改訂履歴に書く
- push の前に、API の `mvnw verify` と画面の lint・テスト・ビルドを手元で全部流し直す（BookLog と同じ）
- 確認のために開発用のデータベースに作ったユーザー・ワークスペースや、開発用のバケットに置いたファイルは、確かめ終わったら消す
