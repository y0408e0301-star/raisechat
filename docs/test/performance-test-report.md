## 1. 結論

**公開先（AWS）で測った結果、負荷のないときは N-1〜N-5・N-7 が目標以内だった。50 人の同時アクセスのときは、検索の「見つからない 2 文字の言葉」（N-5）と、スマートフォンの N-2〜N-4 が目標をわずかに超えた。N-6 は日本から測れず、米国のランナーから測った値（参考）が目標を 1 秒ほど超えた**（2026-11-19）。

## 3. 気をつけること

### 3.1 米国のランナーの値は合否に使わなかった

ランナーから測ると、API の P50 が 240〜260ms になった（手元からは 40〜60ms）。公開先の ALB で見た処理の時間の P50 は 20〜40ms で、ECS の CPU は 20% 未満・RDS の CPU は 45% 未満だったので、差は米国から東京までの往復と考えられる。1 回の画面の操作で API を何回も呼ぶため、画面の値は 1 回ごとに約 200ms 上乗せされ、N-1・N-2・N-4 のスマートフォンなどが目標を超えた。利用者は日本から使う（要件定義書 4 章）ので、合否は手元（日本）から測った値で決めた。ランナーの結果は参考として残す（手元の perf/results/summary-runner-2026-11-18.md。リポジトリには入れない）。

### 3.2 スマートフォン・50 人の負荷のときの N-2〜N-4

同じ 50 人の負荷でも、パソコンは N-2 0.34 秒・N-3 0.46 秒・N-4 0.62 秒で十分に収まり、50 人への通知も k6 では P95 0.18 秒（N-3）・0.13 秒（N-4）で、1,500 件すべて届いた。超えたのは CPU を 4 倍遅くしたスマートフォンだけで、0.05〜0.15 秒の差である。1 台のパソコンで k6（50 人）とブラウザを同時に動かしたことによるブラウザの側の遅れが含まれるとみられる（開発の途中で手元の DB に向けて測ったときも同じ傾向だった。基本設計書 2.4）。ただし、同じ時間に 5.1 の検索で RDS の CPU を使い切っていて、画面の測定と同時の API（最新 50 件 0.56 秒・送信 0.63 秒）も目安の 0.5 秒を超えたので、サーバーの側の遅れも含まれる。

### 3.3 N-6・N-7 は手元から測れなかった

手元の回線の上りが 4Mbps ほどのため、画像 4 枚（40MB）を送るだけで 80 秒以上かかり、「送信」ボタンが押せるようになるのを待つところで止まった（120 秒）。測る条件の上り 30Mbps を満たせないので、手元の値はない。ランナー（上り 30Mbps の条件）から測った値を参考に書いた。N-6 の 15.99 秒には 3.1 の上乗せ（S3 への PUT・complete API・縮小の完了の確かめなど）が含まれ、40MB を 30Mbps で送るだけで 10.7 秒かかる。開発の途中に CI と同じ形（ランナーの中の jar と MinIO）で測ったときは 13.8 秒で目標以内だった（基本設計書 2.4）。

### 3.4 タスクの大きさ（インフラ設計書 未決事項 3）

50 人の同時アクセスと 50 人の WebSocket の接続のあいだ、ECS の CPU は 20% ほどだった。画像 4 枚（N-6）の縮小も、ランナーからの測定で失敗せずに終わった。遅くなったのは RDS の側（4 章）で、タスクの大きさ（1 vCPU・2GB）は足りている。

### 3.5 失敗した応答

失敗した応答は 0.06〜0.20% で、基準の 1% 未満だった。主なものは、測定のために送ってすぐ消したメッセージ（perf-ch-45）を、同じ時間に別の人が既読にしようとした 400 である（機能定義書 FN-14 のとおり、会話にない親メッセージの ID は受け付けない）。ほかに、基準の測定でワークスペースの詳細が 1 回だけ 21.6 秒かかって切れた（P95 は 84ms。続けては起きなかった）。
