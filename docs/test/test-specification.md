## 1. 方針

要件定義書 13.1 のとおり、要件 ID ごとに 1 件以上のテストを用意する。テストはできるだけ自動にし、Pull Request ごとに GitHub Actions で動かす（N-35）。

| 種類 | 何を確かめるか | 置き場所 | いつ動かすか |
| --- | --- | --- | --- |
| API | API の入力・出力・権限・データ（Controller・Service・Repository の単体と、API を通したもの）と、WebSocket の接続・購読・通知（STOMP のクライアントで）。DB は Testcontainers の PostgreSQL、S3 は MinIO | backend/src/test/java | Pull Request ごと（`mvnw verify`） |
| 画面 | 画面の部品と画面ごとの動き。API と WebSocket は偽物にする | frontend/src/\*\*/\*.test.ts(x) | Pull Request ごと（`npm test`） |
| E2E | 本物の API・DB・S3 につなぎ、2〜3 人分のブラウザで利用者の操作の流れとリアルタイムの通知を確かめる。アクセシビリティ（axe）と 375px の横幅も | frontend/e2e | Pull Request ごと（CI は Edge。ほかのブラウザは 3 章） |
| 性能 | 要件定義書 11.1（N-1〜N-7）の時間を P95 で判定する | perf/k6、frontend/perf | 任意のとき（基本設計書 2.4）。公開先では開発計画書 2-8 で測る |
| テスト以外 | 設定・文書を見る、公開先で確かめる | | 検収のとき（開発計画書 2-8） |

## 2. 要件 ID とテストの対応

### 2.1 テストに要件 ID・観点の ID を書く決まり

テストを書くときは、確かめる要件 ID（A・PF・W・I・MB・CH・MS・TH・AT・RE・MN・DM・SR・NT・G・M・N・BR。docs/README.md の ID の一覧）と、機能定義書 10 章のテストの観点の ID（TC-機能の番号-連番。例：TC-03-1）を、次のどこかに書く。ID を書くのは、そのテストが実際に確かめているものだけにする。

| 書く場所 | 例 | どのテストに付くか |
| --- | --- | --- |
| テストの名前 | `it('M-27：見られない会話は general を開く')`、`test('…（N-24）')` | そのテスト |
| テストの直前のコメント | `// BR-9`（JUnit では `@Test` の上） | 次のテスト |
| テストの中 | `// MB-8 相手がいなくなった DM は送れない（M-36）` | そのテスト |
| 区切りのコメント | `// ---- 登録（A-1〜A-4）----`、`// -------- 削除（CH-9、TC-06-8）`、`// ------` だけの行の次の行 | 次の区切りまでのテスト |
| describe・@Nested のクラス名 | `describe('「新着」の線（MS-1）', …)` | 次の区切りまでのテスト |

`A-1〜A-4`・`TC-03-1〜3` のように範囲でも書ける。

対応表は、テストに書いた ID を読むだけで、そのテストが本当にその要件を確かめているかは見ない。ほかの ID を説明するコメントに ID を書くと、確かめていないテストが対応づけられ、`--check` も通ってしまう。そのため、テストの近くのコメントには、そのテストが確かめていない ID を書かない（参照するときは「FN-14 の決まり」のように機能の番号で書く）。ID を足したテストは、Pull Request の自動レビューと、変更した人が中身を読んで確かめる。

### 2.2 対応表

[要件 ID とテストの対応表](requirement-coverage.md) は、`node scripts/requirement-coverage.mjs` がテストのファイルを読んで作る。手で直さない（BookLog と同じスクリプト）。

- 対応表は 1 章が要件 ID、2 章がテストの観点（機能定義書 10 章）。どちらも、確かめるテストを種類（API・画面・E2E・性能）ごとに並べる
- テストのない要件 ID・観点があるとき、または対応表を作り直していないときは、`node scripts/requirement-coverage.mjs --check` が失敗する。GitHub Actions でも Pull Request ごとに動かす
- テストではなく、設定・文書を見て確かめる要件 ID（N-8・N-10・N-12・N-23・N-26・N-32〜N-35）は、確かめ方を対応表に書く（スクリプトの中の一覧で決める）
- 要件 ID の種類のうち、P（前提）・R（リスク）・U（未決事項）・Q（設計で見つけた不足）・SG（セキュリティグループ）は、テストの対象にしない。SG はインフラ設計書と Terraform の検査（tflint・trivy）と、公開先で確かめる（インフラ設計書 8.1）

### 2.3 対応表を作る中で直したこと

対応表で「テストなし」と出た ID は、ほとんどが既存のテストで確かめていて、ID を書いていないだけだった。次のものは確かめていなかった（または一部だけだった）ので、テストを足した。どれもアプリの不具合は見つからなかった。

| ID | 足したテスト |
| --- | --- |
| TC-01-5（A-8） | session.spec.ts：ブラウザを閉じて開き直してもログインしたままで、ログアウトすると G-1 になる |
| TC-03-9 | MemberApiTests：ワークスペースを削除すると、リアクション・メンション・DM も消え、その招待リンクは 410 になる（前はチャンネル・メッセージ・招待リンクの行だけを確かめていた） |
| TC-05-8 | NotificationApiTests：キックされてまた参加しても、入り直していないプライベートチャンネルのメンションは数えず、一覧にも出さない |
| TC-06-9 | channels.test.tsx：チャンネルの名前・説明に入れたタグは、G-14 に文字のまま出る（前は API で文字のまま保存することだけを確かめていた） |
| TC-12-7 | DirectMessageApiTests・AttachmentApiTests：DM でもスレッド・リアクション・メンション・添付が使える |
| PF-8 | ProfileApiTests：プロフィールを変える前に送ったメッセージも、次に読み込むと新しい表示名・ステータスで出る |
| N-31 | messages.test.tsx：送信に失敗しても、入力した文が一覧に残る（MS-13。前は「もう一度送る」だけを確かめていた） |

TC-05-8 の「入っていないチャンネル」は、公開チャンネルを含むと FN-14 の決まり（参加していない公開チャンネルのメンションも数える）と食い違うので、入り直していないプライベートチャンネルのことと書き直した（FN-05 0.4）。

## 4. 手動で確かめる項目

### 4.1 実機

検収のとき（開発計画書 2-8）に公開先の URL を実機で開いて、次を確かめる。ユーザーは 2 人作る（2 台目の端末か、パソコンのブラウザを使う）。リアルタイムの通知は、実機と、もう 1 人のパソコンのブラウザの間で確かめる。

| No | 操作 | 確かめること | 関係する ID |
| --- | --- | --- | --- |
| 1 | ユーザー登録する。ユーザー ID を 2 文字にして「登録する」 | 入力欄の下に M-2 が出る。正しく直すと登録できて G-3 に移る | A-1〜A-4、M-2 |

| 3 | ブラウザを閉じて開き直す | ログインしたまま G-3 が出る | A-8、TC-01-5 |
| 4 | ワークスペースを作り、招待リンクを作って、もう 1 人に渡す。もう 1 人がリンクを開いて参加する | 作ると general が開く。もう 1 人は G-4 から参加でき、general が開く | W-3、I-1、I-4、I-5 |
